Scaled to what this repository actually contains (single-repo customisation): the meaningful
migration on the table is the playwright-bdd major bump; the template's other two standing plans
are assessed against current state.

## Plan 1: playwright-bdd v8 -> v9 (the audit-driven migration, Risk 1)

- **Why:** clears all five moderate advisories (`uuid` via the `@cucumber/*` chain); npm's own
  resolution proposes `playwright-bdd@9.2.0`.
- **Surface to check:** `defineBddConfig({ features, steps, outputDir })` in
  [playwright.config.ts](../../playwright.config.ts) (lines 15-19) and `createBdd(test)` +
  regex-style step definitions with a custom world in
  [tests/calculatorSteps.ts](../../tests/calculatorSteps.ts) - core API, expected stable, but the
  major bump requires reading the v9 release notes before trusting that.
- **Sequence:** branch; bump `playwright-bdd` and remove `tsx` in one change; `npm install`;
  `npm run bddgen` and diff the generated specs under `features/.features-gen/` for shape changes;
  full `npm run verify` **when the sibling tree is not under concurrent use**; confirm
  `npm audit` = 0; record in CHANGELOG `[Unreleased]` and the backlog.
- **Risk:** low - the generated-spec layer isolates most churn, and the suite is 17 checks small.
- **Rollback:** revert the lockfile + `package.json`; no source-layer coupling to v9 features.
- **Do not** combine with the Node-floor or licence changes; keep each independently revertable.

## Plan 2: Single Source of Truth for Features

- **Current status: achieved.** Gherkin under [features/](../../features/) is the sole feature
  source; generated specs (`features/.features-gen/`) are git-ignored build output regenerated by
  every `test`/`test:bdd` run, and the architecture note documents that contract explicitly
  ([docs/project-structure-and-test-architecture.md](../../docs/project-structure-and-test-architecture.md)
  lines 84-104).
- **Residual risk:** none structural. The only second statement of behaviour is the hand-written
  OpenAPI document, addressed by the drift-guard suggestion in
  [05_RECOMMENDATIONS.md](05_RECOMMENDATIONS.md).
- **No migration needed** - keep the ignore rule and the bddgen-before-test coupling as is.

## Plan 3: CI/CD (GitHub Actions) - current status and next increment

- **Current status: solid.** [.github/workflows/ci.yml](../../.github/workflows/ci.yml) gates PRs
  and `main` pushes on the same `verify` sequence a developer runs locally, reproduces the
  two-checkout sibling layout per ADR 0001, redirects the repo-local npm cache so setup-node
  caching works, sets `concurrency` cancel-in-progress, and scopes `permissions: contents: read`.
- **Increment 1 (Risk 9):** upload `playwright-report/` + `test-results/` on failure
  (`if: failure()`, short retention) so CI-only flakes are diagnosable - the repo has already had
  one fast-runner-only flake in its history.
- **Increment 2 (deferred, with the ADR):** pinning the sibling checkout stays gated on
  ADR 0001's external-consumers trigger; this review reaffirms that deferral rather than
  re-opening it.
- **Not needed:** Docker/compose - the application is a single `node dist/startServer.js` process
  started by Playwright's `webServer`; containerising it would be ceremony against KISS/YAGNI
  (N/A - no Docker plan required for this repo).
