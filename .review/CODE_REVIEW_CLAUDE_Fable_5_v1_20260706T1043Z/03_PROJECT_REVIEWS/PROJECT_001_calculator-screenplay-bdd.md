## Architecture and design patterns

- Textbook ports-and-adapters in miniature: the pure domain
  ([src/calculatorDomain.ts](../../../src/calculatorDomain.ts)) knows nothing of HTTP or the DOM;
  the HTTP adapter ([src/calculatorHttpServer.ts](../../../src/calculatorHttpServer.ts)) and the
  browser controller ([src/uiController.ts](../../../src/uiController.ts)) both depend inward
  through the shared contract module
  ([src/calculatorContracts.ts](../../../src/calculatorContracts.ts)). Validation errors and
  unsupported-calculation errors are distinct types mapped to 400/422 in exactly one place.
- The Screenplay implementation is faithful to the pattern's layer discipline: steps only
  translate and stage actors; tasks compose intent (`Calculate.usingTheApi/usingTheBrowser`);
  interactions are the only code touching Playwright locators; questions are the only code reading
  outcomes; abilities (`BrowseTheWeb`, the `PlaywrightApiClient` adapter behind `MakeRequests`)
  own the toolkit handles. No layer leaks downward.
- Consuming the Screenplay primitives from the sibling `hand-baked-screenplay-pattern` package
  rather than copying them is the right call for the teaching pair, and its risks (unpinned
  `file:../`, CI floating `ref: main`) are governed by an ADR with a revisit trigger and a dated
  review log rather than left implicit.

## Code quality and maintainability

- Strict TypeScript with the aggressive correctness flags on
  ([tsconfig.json](../../../tsconfig.json): `strict`, `exactOptionalPropertyTypes`,
  `noUnusedLocals`, `noFallthroughCasesInSwitch`); exhaustive `switch`es over the operator union
  keep the domain closed for modification but open for extension.
- Every file opens with a responsibility statement and a pedagogical-decision note; comments
  consistently explain *why* (the raw-`Buffer` trick in
  [tests/api.spec.ts](../../../tests/api.spec.ts) lines 75-78 is a model example).
- Minor debt: `tsx` is declared but unused (Risk 3), the browser controller's `fetch` path has no
  failure handling (Risk 6), and there is no licence (Risk 2).

## Test coverage and approach

- The pyramid is real, not rhetorical: 7 domain unit tests (including three ISTQB boundary-value
  cases), 6 REST integration tests covering 200/400/422/404 plus health and the OpenAPI contract,
  and 4 business-readable BDD scenarios (2 API, 2 UI) generated by playwright-bdd. Broad
  arithmetic coverage deliberately lives at the cheap layers; the browser pays only for workflow
  proof.
- Synchronisation is state-based: the one asynchronous UI read waits for the controller's settled
  `data-state` attribute ([tests/calculatorQuestions.ts](../../../tests/calculatorQuestions.ts)
  lines 42-49), a fix carried from a real CI flake and documented in both the code and the backlog.
- Isolation posture is honest: one shared `webServer`, `--workers=1` everywhere, and
  `fullyParallel: false` with a comment stating what must change before parallelism is safe
  ([playwright.config.ts](../../../playwright.config.ts) lines 22-25).
- Not verified at runtime in this review: the `verify` gate builds inside the sibling working
  tree, which was under concurrent review, so suite-green claims rest on the CHANGELOG/backlog
  record and CI history rather than a fresh local run.

## Documentation quality

- Unusually strong for the repo's size: README (quick-start honest about the two-repo layout),
  SCREENPLAY.md (primitive-to-example mapping), a flow walkthrough, a toolchain architecture note,
  a keep-a-changelog CHANGELOG, an ADR, and a scored backlog.
- The main documentation defect is currency, not content: `main`'s backlog is two cycles stale
  with its fix waiting on open PR #11 (Risk 4), and the README's Node 18 floor contradicts CI and
  the sibling (Risk 5).

## Strengths

- Previous review cycle (five findings) fully and verifiably remediated in source - a working
  review -> worklist -> fix loop is itself portfolio evidence.
- Business-readable Gherkin that stays business-readable: no selectors, no status codes in
  scenario text, with the 400-vs-422 convention documented in the feature header where a
  stakeholder-adjacent reader can find it.
- Zero runtime dependencies; the static-asset allowlist
  ([src/calculatorHttpServer.ts](../../../src/calculatorHttpServer.ts) lines 166-168) closes path
  traversal by construction.

## Weaknesses

- Dev-dependency audit debt (6 advisories) with a major playwright-bdd bump as the fix (Risk 1).
- No licence on a public teaching repo (Risk 2).
- Small unhappy-path gaps in the pedagogy: unhandled `fetch` failure in the UI controller,
  write-only `Remember`, no CI failure artefacts (Risks 6, 8, 9).
